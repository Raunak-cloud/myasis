# Employer account handling

The applying agent checks the candidate's private, employer-scoped credential metadata before authentication writes. Password forms receive an automatic account-status observation before the first model decision; email-first and SSO pages use `check_employer_account`. A missing local record is not proof that the employer account does not exist.

Accepted credentials are reused. Pending registration and activation preserve their exact proposal across runs and tool-generation recovery. A saved account blocks duplicate registration. Rejected credentials remain unavailable; only Owtomate-managed accounts can enter automated password replacement. New account creation uses the employer's normal account/email discovery where offered and its supported registration flow.

When a complete current employer message establishes that an account exists and no usable Owtomate account record is attributable to it, `check_employer_account` records a private-browser sign-in task and ends this application attempt. A merely filled registration draft is not proof of Owtomate ownership. The task is a versioned `accountAccess` outcome, not an invented screening question, and never asks for a password in the answer bank. Its controlled copy survives run-log import, remains scoped to the candidate/job, and clears through successful application preparation/submission or explicit dismissal. Screening-question answers cannot resolve it. A possible application send always retains its uncertainty and duplicate guard.

SuccessFactors identity includes its company tenant; a company-less redirect retains the bound tenant in the shared recovery record. Other portals are scoped by host and employer. New password derivation includes this realm. Legacy password recipes retain their exact derivation; unassigned shared-host accepted metadata is never guessed into an employer. Existing employer-specific pending proposals remain recoverable. Credential JSON writes retain the existing owner-local cross-process transaction lock and atomic publication.

Sites may intentionally hide account existence. A generic “if an account exists” response remains unknown and must not be reported as proof that the candidate previously registered manually. See [OWASP authentication responses](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html) and [SAP company identity](https://userapps.support.sap.com/sap/support/knowledge/en/2611051).
