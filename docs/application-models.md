# Application models

Admins can choose **Celeris Magnus** or **MiniMax M3.1** on Apply. The choice is saved immediately and applies to the next run. An operator can also select a model in a single admin request without changing saved preferences. Ordinary accounts always use Celeris, including when an old saved preference or a client override requests another provider. Model identities keep fit and draft caches separate.

MiniMax uses `minimax/minimax-m3.1-flash` through OpenRouter. The admin-only `/forms` lab also offers both models. Configure `OPENROUTER_API_KEY` in Admin → Config → Models. The server rechecks the active account's admin status and selects credentials before spawning a worker. API keys never go into account settings or the dashboard bundle. An unavailable selected provider fails explicitly; it does not silently fall back to a different model.

Both models run the same application loop, receive the same offered browser tools, and use the same recovery and candidate-confirmation rules. The applying agent handles its own recovery. No manual or automatic specialist consultation or specialist reporting tools are offered. OpenRouter reasoning blocks are retained unchanged across tool turns. Provider retries only regenerate replies; they cannot replay browser actions. MiniMax uses DOM/HTML observations during ordinary work, with a fresh screenshot on execution errors, stalled recovery or an explicit visual request. Historical images are removed on the next DOM-only turn. Celeris retains its every-turn screenshot default; the MiniMax policy also applies to the forms lab despite legacy screenshot settings.

Authentication tools declare their input-selection alternatives in the shared schema: credential filling requires `targets` or `refs`; code entry requires `targets`, `ref` or `refs`. Empty selections are rejected before browser or mailbox work. Rejected arguments are failed tool calls in the admin diagnostics and recovery flow, and cannot count as successful browser mutations. The agent still chooses every input and repair.

OpenRouter's `usage.cost` is the billing source when present. Otherwise the meter uses published non-discounted token rates; absent usage reserves estimated input and the requested output allowance and records the final charge as unknown. Every generation, including an incomplete reply, counts toward the same per-application budget. These amounts are USD; Celeris and OpenRouter have separate account balances.

For a fair synthetic comparison, keep the form seed, fictional candidate, tools, screenshots, base/progress budgets and time allowance identical. Give each attempt a unique email challenge namespace to prevent old verification emails or delivery idempotency keys from contaminating a retry. Report independent employer receipts, elapsed time, all model charges, tool errors and successful recoveries. A single paired trial is a smoke comparison, not a general reliability benchmark.

Candidate-evidence searches rank exact-token passages with BM25 and return only matches. Exact document IDs and empty-query pagination retain access to complete sources; a search miss is never treated as proof that a fact is absent. This keeps generic policy language and unrelated saved answers from consuming the first response. References: [BM25](https://www.elastic.co/blog/practical-bm25-part-2-the-bm25-algorithm-and-its-variables), [tool response design](https://www.anthropic.com/engineering/writing-tools-for-agents).

Repeated identical evidence responses on an unchanged form now enter the shared recovery flow, including alternating queries. The agent receives a pagination/reuse advisory, deeper reasoning and reuse/pagination guidance for the applying agent. No second agent is called. Reads are not browser progress or budget credit; new evidence pages and genuine form changes remain valid. No form action, answer, submission or fixed step limit is imposed by this detection. The owner-supplied concise system prompt leaves recovery strategy to the applying agent.

The applying system prompt permits reasonable inference from candidate evidence, explicitly giving Australian citizenship/nationality as an example. It authorises accepting application terms, privacy notices and consent checkboxes without asking. Only genuinely required personal information unavailable from the evidence is requested from the candidate. Mode, approval, account and existing execution controls remain in effect.

The applying agent now uses the owner-supplied concise system prompt verbatim, replacing only the saved cover-letter-instructions placeholder at runtime. Recovery policies, provider completion text, suitability instructions and duplicate writing-style blocks are no longer appended to its system message. Application mode, selected-job authority, candidate evidence and approval details remain run context. Tool contracts and existing execution controls are unchanged.

Snapshots are offered only through `browser_action` with `action: "take_snapshot"`, including optional screenshots and scoped targets. The duplicate standalone applying-agent tool has been removed; all other tools retain their existing availability. Historical snapshot names remain recognizable in audit/transcript handling.

The applying agent can call `test_application_helper` directly to design and test an attempt-local helper from its available browser/document primitives. Successful helpers become named tools on its next turn and run through the same normal executors. Failed tests return feedback without touching the live form. This uses the existing isolated helper engine and does not restore specialist consultations or append instructions to the owner-approved system prompt.
