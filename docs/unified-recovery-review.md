# One recovery reviewer

The applying agent alone chooses browser actions, grounded answers and proposed outcomes. The code owns the browser executor, single-writer recovery lease, evidence revisions, cost/time budgets, candidate approval and send/receipt boundaries. The recovery reviewer is read-only: it combines troubleshooting and checking proposed stopping decisions. There is no separate AI stopping supervisor, including for the admin pilot. The process watchdog remains independent.

Manual help, stalled progress, proposed technical errors and proposed missing-answer stops use `reviewApplicationRecovery`. Its existing `consult_application_specialist` tool name remains a compatibility alias. All paths share the same selected provider, original application meter and two-consultation allowance. Three executed repair approaches remain bounded by the existing recovery ledger; a consultation, rejected report, checkpoint or restart does not reset them. Provider/report errors never force a skip or manufacture a candidate question.

The applying loop awaits the entire consultation before executing another command. An owner-local review lock rejects overlapping requests, and the durable writer lease rejects a second writer. Reviewers may test existing helper primitives only on isolated synthetic fixtures. They never receive the live executor. Candidate approval, prepared-document byte checks and the canonical accuracy review remain authoritative for all sends.

Before consultation the code reads the existing page, saved form and full accessibility snapshot. It supplies one versioned, credential-redacted evidence packet to both the reviewer and applying agent. Up to 50,000 characters are retained, with document/validation excerpts preserved when a page is larger. This is a bounded view, not proof that omitted content is absent. The ordinary compact observation stays bounded. Reinspection after consultation reads the existing page again: it never reloads or navigates. A changed page, attachment, saved value or candidate/owner evidence revision invalidates the advice. Unsaved inputs and native file selections remain untouched. Current evidence survives ordinary observation compaction only while that observed state still matches.

Reviewer goals must be achievable before submission, such as verifying the approved letter. The applying agent may follow a supported alternative, reject stale advice, ask an actual securely captured required question, or preserve a technical error checkpoint. Technical stops are distinct from unsuitable jobs. Evidence-based disagreement does not create an independent controller or an unbounded review loop.

Approved cover letters do not require a separate code-level attachment or inline-delivery proof to pass preparation or final submission. This includes candidate-revised approved letters. The applying agent still owns entering or attaching the approved content and checking employer acceptance; approval alone must never be recorded as a completed upload. Observed different letter text, required employer fields, supporting-document upload requirements, exact resume consent and actual submission receipts retain their existing checks.

After a possible send, automatic repair/reviewer escalation is disabled. An explicitly requested review may inspect the employer response read-only, without helper construction or any new send authority. Uncertain delivery still requires investigation before another send. A retryable error preserves recovery work; it does not schedule an automatic replay or grant new candidate approval.

Validation covers long review pages, preserved unsaved answers/uploads, same-URL asynchronous changes, overlapping reviews, selected-provider/shared-budget behavior, malformed reports, three-approach limits, missing candidate answers and approval/receipt boundaries. Browser cases use fictional candidates and isolated routes; they do not apply to real jobs.
