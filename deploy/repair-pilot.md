# Admin recovery pilot

Only active admin account 1 (`raunak.vision@gmail.com`) is enrolled. Install after
the normal deployment: `bash deploy/install-repair-pilot.sh --enable` as root.
Future deployments refresh the service without resetting its activation time.

The root-owned config is `/etc/owtomate-repair-pilot.json`. Set `enabled` to false
to pause. The broker and dashboard recheck it before work and retries. Scheduled
incidents also require their original schedule to remain enabled.

MiniMax proposes changes in four named browser/file modules, without shell,
browser, candidate text or credential access. A separate review, static checks,
networkless dynamic-user build and fixed regression suite must pass. A compiled
build under `/opt/owtomate-repair-releases` is immutable, revision-bound and expires
after two hours. Generated code never replaces the shared production release.

After a localized internal tool execution exception (or repeated older unclassified failure), the application pauses at a safe checkpoint within its original run for up to six minutes. Invalid/stale targets and unlocalized browser timeouts remain with the applying agent. The coder receives a fixed error category and only verified internal module/function identifiers, never raw stack traces. Public Page contracts distinguish corrupted browser arguments from genuinely missing frames without forwarding candidate data. Source snippets are normalized across Windows and Unix line endings; a valid small edit batch proceeds directly to review. The validated build resumes the same browser page once; the run does not end or restart.
The in-memory continuation retains verified answers, private generated documents, pending credentials and the original spending meter. Shared runtime bridges preserve credential redaction, account/worker identity, quota and reservation callbacks, and cost accounting. Normal duplicate, account, entitlement and candidate approval gates remain.
Semi auto prepares; confirmed applications retain their exact approved revision.
Before an enrolled admin agent stops as skipped or Needs attention, a fresh read-only review compares its claim with current browser values and authoritative candidate sources. It uses the selected application provider and original meter, permits at most two review requests per original application, and preserves its counters across a tool repair. Rejected stops refresh stale reasoning without changing browser state. Grounding failures, exhausted budgets and prior send attempts cannot gain permission from this review. Other accounts retain their existing behavior.
The source gate uses bound browser types and API provenance to distinguish browser ownership references from account ownership. Unknown, cast-only or account-derived ownership stays protected; imports, I/O, approval, credentials and submission controls remain frozen.
Stopping reviews cite stable source records; only original record contents reach the applying agent. Send intent is validated before dispatch in confirmation modes. Traces distinguish rejected calls from started operations; an older or uncertain call never gains the new non-execution proof retroactively.
After a rejected stop, the terminal tool is withheld until a browser attempt or fresh read-only evidence inspection. Canonical, credential-redacted candidate context is refreshed without another model request. Unknown personal answers can still be checked through read-only evidence tools.
The enrolled MiniMax trial explicitly selects `target_mode`. A selected ref/selector/locator ignores unused pointer and coordinate placeholders; a missing selected target cannot fall back to another one or to the keyboard. Coordinate mode is excluded from Semi auto schemas and remains blocked by execution controls. Legacy calls retain their existing precedence. Empty unused script/receipt metadata is accepted only where it cannot execute code or claim a receipt; actual scripts, waits and completed receipts retain their required evidence.
An independent review rejection permits one revised proposal from the original source, sharing the same eight coding turns and US$0.50 case cap. Every proposal must pass the unchanged static checks and an independent review. Static denials remain terminal. Both proposals and review decisions are retained separately.
Deployment keeps admission closed throughout: the `draining` lock permits existing workers' immutable repairs; `building` and legacy empty locks block repairs before shared files change.
Missing send evidence, unresolved candidate questions, stopped runs and uncertain
sends block recovery. No function is replaced while an action is in flight. The prior attempt removes its listeners before the tested generation continues on the existing page. Other applications and customers retain their original code.

Limits: one case per original run, two cases per Sydney day, eight coding turns,
three changed files, 100 changed lines, one in-run continuation. Separate after-run recovery launches are disabled in this mode. Coding and review costs are
stored in `repair_pilot_cases`; further calls stop when reported spend exceeds
US$0.50 (an in-flight response can cross that threshold). Provider failures and
unknown usage are recorded rather than treated as zero. Application-agent usage
is separate and retains the account's selected application provider.

Inspect `journalctl -u owtomate-repair-pilot.service` and `repair_pilot_cases`.
Source proposals, independent review decisions and validation logs stay in `/var/lib/owtomate-repair/cases`,
root-only. Normal owner-scoped traces and database application outcomes remain
the authority for whether an application was actually prepared or submitted.
