# HR outreach

This release is administrator-only. The interface, HTTP APIs, queue, final send claim and Gmail transport require a current administrator account. Regular users cannot see or enable HR outreach. Administrators enable **Email hiring teams after I apply** in Submitted Applications. Each applied role has an HR email action with its latest status; opening the role shows its recipient, exact message, public source, delivery status and all attempts. Historical roles fetch their own owner-bound email history, independently of the latest history page. There is no separate HR emails tab. It starts disabled for existing accounts. Enabling it does not contact employers from historical applications. Turning it off cancels unsent work.

The independent application service runs the HR worker after a complete run finish, with a 30-second periodic check as a recovery fallback. Every new application carries its actual server-owned submitting run ID, including Auto and approved email submissions. HR waits for browser and descendant cleanup, successful result saving, final run-record persistence and release of the application slot. Only then is the run marked HR-ready and the worker awakened. An application appearing early in the database or an exited worker is insufficient. Historical rows are never assigned to runs by timestamps. Prepared, failed, unconfirmed and already-applied records do not create outreach. The HR agent has its own system prompt and writes a brief, factual email using the candidate's profile and submitted cover letter. It does not modify the applying-agent prompt or search preferences.

The Run screen shows HR progress inside the Activity box, without a separate Apply-page card. Finding contact, Contact found, Sending email and Sent are visible stages, alongside waiting, writing, delivery checking and truthful final counts. Progress is owner-scoped and updates every five seconds. The Run screen requests only a small progress summary, without downloading the email history. Status polling preserves expanded per-role messages; administrators retain the opt-in control in Applied. Ordinary users make no HR requests.

Discovery checks the public employer site before corroborated public sources. Brave search uses the configured provider key without a daily HR search quota. Daily usage is counted atomically for cost visibility, independently of the job catalog's discovery allowance and external database. Each lookup retains its existing page, query and time bounds. No address is guessed. Recruitment mailboxes and publicly identified hiring-manager contacts are eligible; unrelated support, sales, privacy, security, job-board and no-reply addresses are excluded. Existing robots-aware, DNS-pinned HTTPS crawling bounds pages, redirects, time and request size. Published no-email notices are respected.

If the first lookup returns no suitable contact, a second AI research stage can choose new public searches, read pages and follow links. It uses the existing Minimax/OpenRouter and Brave services, with high reasoning, without a new verification subscription. Its only tools are `search_public`, `read_public_page` and `finish_research`; it has no candidate profile, Gmail or send access. It receives only employer/vacancy public evidence and prior source diagnostics. Search results and page observations, rather than model-written addresses or excerpts, feed the existing employer/contact verifier before composition or sending. The monthly public-contact cache and confirmed-invalid exclusions apply to both stages.

Additional research has a 180-second deadline, up to 12 model turns, 8 searches and 12 page reads, with a US$0.10 measured-use stopping point between model calls. Actual research usage is saved even when no contact is found and counts toward the existing HR budget. The whole HR attempt allows eight minutes within its ten-minute lease. Incomplete, unavailable and blocked research cannot become a definitive claim that no contact exists; it records an incomplete result for the existing retry process. Completed negative results say no suitable contact was found in the sources checked. Existing negative-cache contexts are refreshed once for this expanded research version. Public search/page text is untrusted data, and source instructions cannot grant new tools or access.

HR public reads now distinguish a verification challenge from robots refusals, ordinary access denials and sign-in pages. A robots-approved challenge can open in a disposable browser and use the existing configured CapMonster adapter for supported types. The same wrapper serves the first lookup, AI research, final source verification and monthly revalidation. It reuses a result within one lookup so the same URL cannot repeatedly purchase solutions. Browsers have no saved candidate profile, Gmail session or downloads. Navigation and assets are checked for public destinations; top-level navigation stays on the original origin, redirected pages receive their own public-crawler permission checks, and form submissions are blocked. Only verification-related background POSTs are allowed. The page must become readable after a solve; a token or reported solver success is insufficient. Cancellation closes the browser. Robots exclusions, login requirements, unsupported checks, missing configuration and unsuccessful solves remain explicit failures, rather than triggering guessed contacts or emails. Controlled `verification_started`, `verification_cleared` and `verification_failed` source events are retained internally. CapMonster uses the existing account/credits; no credentials or clearance cookies enter the shared contact cache.

Only public contact evidence is shared between accounts. It is valid for one calendar month and revalidated in the background, including between runs. Reuse also checks the current vacancy's employer association, so a shared name alone does not select a cached company. Failed revalidation never renews an expired contact. Clean negative lookups are cached for one day; transient discovery failures retry rather than becoming permanent no-contact decisions.

Contact selection keeps four questions separate: which organisation actually employs the applicant, whether the public address belongs to that organisation, whether its hiring remit fits this role and region, and how recently the source was checked. A job-platform footer, sales/network-access address or unrelated specialist recruiter is not an employer hiring contact. Discovery prefers the vacancy's explicit recruitment contact and official company careers/contact/team pages, followed by attributable public sources. JobPosting `hiringOrganization` links help establish employer identity; a publisher's branding does not. Search excerpts are labelled as indexed evidence rather than claimed to be freshly read source pages. Public email obfuscation may be decoded, but mailbox patterns are never invented.

The worker also uses an exact, owner-bound saved public vacancy description and the submitted job's location. The bounded journal reader checks listing identity, source URL, run or application-time association and observation age, then projects only public vacancy fields. Candidate answers, profile, cover letter and agent notes never enter contact discovery or the shared cache. A masked `••••@employer.example` may corroborate a domain; its missing local part is never reconstructed. Recorded advertisement contacts retain their original observation time and `stored_vacancy` provenance, so reuse does not renew publication validity. A negative lookup is cached only for its vacancy/evidence context; another role or changed public evidence gets a fresh lookup.

Careers subdomains and regional recruitment pages take precedence over product/service navigation. Ownership metadata can associate a regional legal entity with its parent trade brand without treating a job publisher as the employer. Escaped or quoted links are normalized before resolving them. Competition and marketing-post context cannot become hiring authority merely because a company-wide recruitment description appears nearby. History distinguishes the original source date from the current lookup, and identifies saved advertisements, search excerpts and public pages separately.

Every lookup records `found`, `no_contact`, `company_unverified`, `access_blocked`, `temporarily_unavailable` or `incomplete`, with bounded internal stage/source diagnostics. Robots/access refusals, unknown company identity and exhausted research are no longer reported as a generic provider outage. Only temporary/incomplete lookups enter automatic retry; the history shows the actual retry date only while another attempt is eligible. No-contact decisions do not fabricate a recipient. Legacy failures whose exact cause was not recorded say so explicitly. Internal provider payloads, candidate evidence and exception stacks are excluded from the customer API and logs.

Contact quality and sending remain separate. A retrospective audit can mark an actual sent email **Contact needs review** without rewriting its recipient, content, receipt or Sent status, and without resending it. Invalid platform contacts are removed from the reusable public cache. A public source check is not mailbox verification, and Gmail acceptance/Sent evidence is not proof of inbox delivery, a read or a reply. Some employers publish no hiring email; no implementation or email verifier can guarantee zero failures.

After a send, automatic read-only Gmail checks inspect authenticated return notices for seven days. They correlate the exact original Sent message, recipient and stable reference. Checks back off from five minutes to daily; no notice means delivery remains unknown, never “Delivered”. An authenticated permanent failure is shown as **Delivery failed**, with its reason, while preserving the original sent message and receipt. Temporary delays and policy rejections remain distinct. Only a confirmed nonexistent recipient (550 5.1.1) excludes that public business mailbox from future discovery, cache reuse and sends across accounts; monthly source revalidation cannot restore it. Raw private return notices are not stored in the shared public-contact registry or shown to customers.

A deliberate invalid-address retry creates a separate numbered attempt after finding another suitable published contact. The original send remains unchanged, and one successor per attempt prevents concurrent retries from creating duplicate emails. Regional recruiters' public invitations to send relevant CVs may provide an alternative after employer identity is verified. No replacement address is guessed. Bounce handling follows [RFC 3464](https://www.rfc-editor.org/rfc/rfc3464); Gmail originals are read through the existing connected account, including [raw message retrieval](https://developers.google.com/workspace/gmail/api/reference/rest/v1/users.messages/get) for OAuth connections.

The November 2026 implementation review used primary documentation: [Google employer identity](https://developers.google.com/search/docs/appearance/structured-data/job-posting), [Hunter public versus inferred sources](https://help.hunter.io/en/articles/1922677-how-does-hunter-find-email-addresses), [Hunter verification limits](https://help.hunter.io/en/articles/15899247-email-verification-faqs), [Snov verification statuses](https://snov.io/knowledgebase/email-statuses/), [Brave search and snippets](https://api-dashboard.search.brave.com/api-reference/web/search/post), [Gmail send receipts](https://developers.google.com/workspace/gmail/api/reference/rest/v1/users.messages/send), and [Gmail later bounce reports](https://support.google.com/mail/answer/6596). The resulting approach uses the existing search/crawl service and does not introduce a paid contact-data integration.

Emails use the account holder's connected profile Gmail, through their selected OAuth or browser connection. No application credits or run allowances are consumed by outreach. The worker sends at most 50 HR emails per user per rolling day, with a measured drafting allowance of US$1 per user per rolling day and at most four automatic attempts before attention is needed. Email bodies contain no attachments or tracking pixels.

A durable unique record prevents another outreach email for the same user, employer and role, including duplicate listings across job boards. `sending` is written before delivery. A crash, lost provider reply or lost receipt write becomes `unconfirmed`, never a fresh send. Reconciliation checks the exact stable reference in Sent. No matching subject alone is accepted as proof. Users can see recipient, full exact message, time, status and public contact source; history is owner-scoped and paginated.

The worker reserves the account browser slot and never kills an existing browser to acquire its profile. Dashboard restarts do not stop it. Deployment and service shutdown wait for current HR work. Account deletion removes all private outreach messages/settings; the public employer contact cache contains no candidate evidence.

HR browser failures retain the failing profile/route/launch/page/mailbox step, its elapsed time, a recognised error category and native network code where available. The redacted original first error line is saved in the private `lookup_diagnostics.browserFailure` field and the correlated `[hr-outreach]` server log. Launch commands, page contents, URL credentials/query strings, email addresses and secrets are omitted. Unknown causes remain explicitly unclassified. Customer history uses a plain explanation when Gmail could not be opened before sending; it does not claim Gmail rejected that email. This instrumentation does not change timeouts, retries, sending or uncertain-send handling.

Run `node ../seek-bot/node_modules/tsx/dist/cli.mjs scripts/test-hr-outreach.mts` from dashboard. It includes real PostgreSQL TEMP-table checks, middleware/access checks, desktop/mobile UI tests, model/transport simulations, lost-receipt recovery and Chromium Gmail fixtures. Tests do not send real email. Normal deployments run this suite under a bounded deadline.

Verification detection also recognises Cloudflare inline bootstraps and challenge headers, and structured PerimeterX security responses. Unsupported types are reported as unsupported, not treated as readable pages. Internal research diagnostics retain controlled failure codes, the attempted action and source URL without query strings, model conclusion, stop reason and per-stage usage counts. Raw provider payloads and stacks are excluded. Customer reasons describe the observed blockers in plain language. These diagnostics do not change contact selection or email-send eligibility.
